# 5.12.8

Arreglo del **doble audio** y del **retardo** de la voz. El culpable era el
**watchdog** que esperaba 1 s a ver si sonaba la voz del navegador y, si no,
lanzaba la online: cuando la web arrancaba tarde, se oian **las dos**, y
siempre habia que esperar ese segundo. Eliminado: la eleccion es ahora
**sincrona** y sin solape.

## El problema

Para cubrir el caso "Linux sin speech-dispatcher" (Web Speech API existe
pero no suena) se puso un temporizador:

> lanza la voz del navegador; si a 1 s no ha arrancado, reproduce online.

Efectos secundarios:

- **Doble**: si la voz del navegador arrancaba a 1,2 s (mas lento que el
  temporizador), sonaba ella **y** la online.
- **Retardo**: incluso cuando la online iba a usarse, habia que esperar el
  segundo del temporizador.

## Cambios

- **Fuera el watchdog.** La decision navegador/online es **sincrona**: si el
  navegador tiene Web Speech API **y** voces, se usa; si no, online. Nunca
  se espera.
- **Motor por defecto: `Online`** (StreamElements). La Web Speech API no
  suena en muchos Linux, asi que el default fiable es el online. Se puede
  volver a *Navegador* en cualquier momento.
- **Migracion automatica en Linux**: si tenias *Navegador* guardado y estas
  en Linux (sin Android), pasa a *Online* una sola vez
  (`rondo.api.vozLinux`). Tu eleccion posterior manda.
- **Guarda de generacion** (`_ttsGen`): cada nuevo aviso incrementa un
  contador; las descargas lentas de un aviso viejo se descartan y **no
  suenan encima** del nuevo.
- **Cache de audio** (`_ttsCache`, hasta 40 frases): repetir la misma frase
  suena al instante, sin volver a descargar ni decodificar.
- El boton **Probar voz** reporta el resultado sin el texto del watchdog.

## Como queda

| Motor | Camino |
| --- | --- |
| Online (defecto) | cache -> GM -> Web Audio; si no, blob; si no, Google |
| Navegador | `speechSynthesis` si hay voces; si no, Online |
| Google | Google via GM -> Web Audio -> blob |

Sin esperas y sin solapamientos.
